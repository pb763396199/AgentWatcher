# 第一轮施工：查清根因并修复（含调试记录）

# 调试：筛选流程 todo 提示步骤环境性失败

## 现象

`npm run test:tauri:flow -- 筛选` 的 `verifyTodoWorkspaceScope` 步骤报「临时 todo fixture 写入后仍未显示 ready nudge」。2026-10-14 修复前三跑三败（隔离双实例两轮、附着主检出旧代码对照一轮），错误一致。历史失败可追溯至该步骤引入（2026-06-15，`4971a2b`）之后在忙碌开发机上的偶发。

## 怎么复现

1. 开发机有若干真实会话在跑（多个工作区 waiting/running）。
2. 跑 `node tools/tauri-realtest/cli.mjs filtering --isolated-runtime`（修复前的代码）。
3. 稳定失败在 todo 提示步骤，10 秒等待超时。

## 提过哪些假设，逐个怎么排除的

| 假设 | 怎么验的 | 结论 |
| --- | --- | --- |
| 另一个常驻实例用内存态覆写共享的 todos.v1.json（待办原本的怀疑） | 失败路径插桩读文件：fixture 仍在（hasFixtureTask=true，mtime 未变）；单实例隔离轮同样失败 | 排除 |
| fixture 选中的工作区在重载后出现活跃会话，nudge 被 workspaceHasActiveSession 抑制 | 插桩读目标工作区卡片状态：唯一卡片 idle | 排除 |
| Rust 侧 get_todo_state 有缓存或读不到新文件 | 失败当场在页面里调 window.__TAURI_INTERNALS__.invoke('get_todo_state')：返回内容含 fixture（hasTargetKey=true） | 排除 |
| 启动时 tauriInvoke 未就绪走浏览器分支（localStorage 空） | 读启动代码：模块顶层 await 保证 tauriInvoke 先于任何启动逻辑赋值 | 排除 |
| normalizeTodoState/normalizeTodoTask 把 fixture 任务丢掉或重键 | 读两个函数：任务保留、键重算但不丢任务 | 排除 |
| todoState 加载后被其他窗口的事件载荷覆盖 | 事件只在保存后广播，无触发路径；采样实验显示重载后「先等待再重置」就能看到 nudge 出现 | 排除（现象指向重置步骤本身） |
| **resetMainFilters 的 fill('') 把焦点留在搜索框，输入守卫无限推迟 todo 渲染** | 读守卫代码（shouldDeferInputInterruptions：activeTextInputElement 聚焦即推迟，无超时）；修复前流程顺序是「重载 → 立即重置（fill 聚焦）→ 等 nudge 10 秒」；在 resetMainFilters 末尾加一行 blur 后，单实例与双实例各三轮全绿 | **证实** |

## 根因

应用的输入守卫 `shouldDeferInputInterruptions`（`ui/index.html`，提交 `abe6394` 2026-06-05 引入）在有文本输入框聚焦时无限推迟 `renderTodoEverywhere`，这是「用户打字时不打断界面」的有意设计。测试的 `resetMainFilters` 用 Playwright `fill('')` 清空搜索框后焦点留在输入框上；fixture 重载路径里重置跑在启动期 todo 渲染刷出之前，nudge 的渲染被推迟到焦点离开为止——而测试从此不再移开焦点，10 秒等待必然超时。测试引入（2026-06-15）晚于守卫引入（2026-06-05），测试生来就带这个竞态，忙碌机器上重置稳定赢过启动渲染。

## 怎么修的

`tools/tauri-realtest/cli.mjs` 的 `resetMainFilters` 末尾把焦点 blur 回 body（提交 `d2853cc`）。被推迟的渲染由输入守卫的定时刷新立即刷出。顺带把失败路径改成携带诊断输出（todo 文件是否仍含 fixture、Rust 侧 get_todo_state 摘要、nudge DOM 与目标工作区卡片状态），下次再坏不用重新插桩。

# 筛选流程的 todo 提示步骤不再环境性失败

## 原始请求

用户原话（2026-10-14）："继续做既有问题待办"。待办正本：`workflow/todo/筛选流程todo提示步骤在双实例下易失败.md`，由任务 `nf31t3pn`（搜索栏按会话 ID 过滤）期间的对照实验产生。

## 目标

`npm run test:tauri:flow -- 筛选` 在开发机另有一个常驻 AgentWatcher 实例的环境下也能稳定全绿。

## Why

2026-10-14 该步骤三跑三败（新代码两轮、旧代码对照一轮），错误一致：「临时 todo fixture 写入后仍未显示 ready nudge」（`verifyTodoWorkspaceScope`）。待办里只有两个未验证假设：常驻实例用内存态覆写共享的 `%APPDATA%\AgentWatcher\todos.v1.json`；fixture 选中的工作区在重载前后出现活跃会话，提示被抑制。

## 范围

做：

- 稳定复现，收集证据，把假设逐个证实或排除，落 `debug.md`。
- 针对根因修复 `tools/tauri-realtest/cli.mjs` 的 fixture 写入与 nudge 等待路径，并先加一个在当前环境下会失败的回归断言。
- 修复后在「另有一个常驻实例在跑」的环境连续多轮验证筛选流程。

不做：

- 不动筛选流程的其他步骤（provider、搜索、空状态、ID 搜索断言）。
- 不改应用（`ui/index.html` 或 Rust）的功能行为；若根因证明出在应用侧，停下来问再动。

## 强约束

- 修复不得用吞错或无条件跳过盖住断言：跳过必须带可查原因并写进结果输出。
- `todos.v1.json` 是用户真实数据：测试的备份与恢复语义必须保持，失败路径也要还原。

## 设计取舍

| 方案 | 怎么做 | 代价 | 结论 |
| --- | --- | --- | --- |
| 测试侧重置后归还焦点 | resetMainFilters 末尾把焦点 blur 回 body，被输入守卫推迟的 todo 渲染立即刷出 | 一行；不改变被测应用的任何行为 | 采用（提交 d2853cc） |
| 重排等待顺序：重载后先等 nudge 再重置过滤器 | 不持有焦点的窗口期里启动渲染自然完成 | 隐式依赖启动时序，慢机器上仍可能输给重置步骤 | 不采用 |
| 应用侧改渲染策略 | 让 nudge 在文本框聚焦时也渲染 | 改掉「用户打字时不打断界面」的有意行为，越出本任务边界 | 不采用；确要改另开任务 |
| 什么都不做 | 维持现状 | 筛选流程在开发机上三跑三败，不可用 | 不采用 |

根因（证据见 debug.md）：resetMainFilters 的 fill('') 把焦点留在搜索框；应用的输入守卫 shouldDeferInputInterruptions（提交 abe6394，2026-06-05 引入）在有文本输入框聚焦时无限推迟 todo 渲染；fixture 重载路径里重置跑在启动渲染刷出之前，nudge 永远不渲染。

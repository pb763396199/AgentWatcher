# 第一轮施工：kill-on-close 作业接管常驻子服务（含调试记录）

## 做了什么

- `src-tauri/src/lib.rs` 新增 `KillOnCloseJob` 与 `spawn_in_kill_on_close_job`：CREATE_SUSPENDED 起进程、挂入 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 作业、经线程快照恢复主线程；非 Windows 平台退化为普通 spawn。
- `ensure_codex_app_server` 与 `start_owned_opencode_web_server` 改用该辅助；两个服务结构体持有作业句柄；`stop` 走 `TerminateJobObject`；退出钩子补调 `shutdown_opencode_web_server`（此前 opencode 连正常退出清理都没有）。
- `src-tauri/Cargo.toml` 给 windows-sys 加 `Win32_System_JobObjects` feature。
- 回归测试 `job_handle_drop_terminates_whole_descendant_tree`。代码提交 `600df71`。

## 现象与复现

2026-10-14 清理两个已完结任务的 worktree 残留时发现：两台测试 GUI 壳退出后，各留下一组 codex app-server 孤儿（`node codex.js` 与 `codex.exe`，CWD 钉在 worktree 的 `src-tauri`），存活数小时，占监听端口、钉住目录句柄导致 worktree 删不掉。用 PEB 读进程当前目录的脚本定位（`.tmp/find-lockers.ps1`）。

## 假设与排除

| 假设 | 验证 | 结论 |
| --- | --- | --- |
| 杀软/索引器临时句柄 | 等待后重试删除仍失败；按进程 CWD 全量扫描命中具体进程 | 排除 |
| 退出清理没执行 | 读 `run()` 事件处理：`RunEvent::Exit` 有调 `shutdown_codex_app_server` | 排除（清理有执行，只是杀不动树） |
| **清理只杀直接子进程** | `Child::kill` 即 TerminateProcess，只作用于直接子进程；spawn 链是 `codex.cmd → cmd.exe → node codex.js → codex.exe` 三层以上，孙进程不在杀伤范围 | **证实（路径一）** |
| **强杀宿主时清理根本没机会执行** | 复现：taskkill /F 宿主后整树存活（修复前代码的历史证据：两台壳被强杀/关闭后孤儿全在） | **证实（路径二）** |
| opencode serve 同样泄漏 | 读 `start_owned_opencode_web_server`：同模式 spawn，且退出钩子没有对应 shutdown | 证实，同源缺陷并入 |

## 根因

引入提交 `28a8a65`（2026-06-08，接入 Codex 桌面会话）。`Child::kill` 的语义只覆盖直接子进程，而服务是多层进程树；宿主被强杀或崩溃时连这个不完整的清理也不会执行。Windows 上正确的生命周期绑定是 Job Object 的 kill-on-close：宿主无论怎么死，系统关闭句柄时整棵挂进作业的树一起终止。

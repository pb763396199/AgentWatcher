ChatGPT 桌面端 imagegen 生图进度条逆向报告

研究对象：ChatGPT 桌面版（Windows，owl shell）26.1029.7803.0 逆向日期：2026-11-05 方法：app.asar 解包 + 当前版本二进制逐字验证

结论（TL;DR）

进度条是“假”的——纯客户端按墙钟耗时模拟，服务器从头到尾不下发任何进度信号。 归一化时间 t = 已耗时ms / 45000，经一组控制点分段线性插值： 0s→3%、4.5s→25%、24.75s→58%、38.25s→88%、45s→90%；超过 45 秒后按 90 + 10·(1 − e^(−1.5·(t−1))) 渐近逼近，99% 封顶、永不显示 100%， 真图到达时占位组件（连同徽章）直接卸载换图。起点时间戳也不来自服务器：客户端第一次观察到 src == null 的 pending 生图条目时自己记下 Date.now()。

2. 桌面端 imagegen 怎么运作（完整链路）

桌面壳（Electron 主进程）完全不参与生图：主进程 bundle 里搜不到任何生图 IPC， 生图是 webview 里的 React 应用直接对 chatgpt.com 后端（backend-api）发起的 SSE 会话流。链路如下：

  1. 请求侧：用户要图时，前端给会话请求追加 system_hints: ["picture_v2"]（函数 T6：只要触发图片意图就补这个 hint），并带上 dalle: { from_client: { operation } } 消息元数据标记本次操作（生成/编辑）。
  2. 服务端流式返回：模型先产出一条 recipient 为图片工具的 assistant 消息。工具名匹配器 PF/Plr/Flr 认三个名字：image_gen、image_gen.text2im 和混淆代号 t2uay3k(.sj1i4kz)（text2im = text-to-image 的内部叫法）。
  3. 进行中标记：这条消息的 metadata 携带旗标：image_gen_task_id（异步任务 id）、image_gen_async、image_gen_multi_stream（多图并流）、ui_card_shimmer（占位微光卡）。命中任意一个，客户端就映射出一条 runtime 条目：{ id: image_gen_task_id ?? 消息id, type: "generated-image", src: null, status: "in_progress" }。
  4. 成品回填：生成完成后，服务端补一条 tool 消息，content_type: "multimodal_text"，内容 part 是 image_asset_pointer（含 asset_pointer、宽高、generation_id）。聚合层把它挂成附件 kind: "media_generation"、generation_type: "image_gen"。至此才有 src，状态翻成 completed。
  5. 关键否定证据：整个 webview bundle 中不存在 partial_image / partialImage / progressive_image 等字段，也不存在 estimatedSeconds / etaSeconds / timeRemaining 等服务端 ETA 字段 —— 对话通道的生图过程对客户端是个黑盒：没有中间图，没有百分比，没有预计时间。
  6. 渲染侧：会话转录把 generated-image 条目聚成 generated-images 组；pendingPlaceholderCount 统计 src==null && status=="in_progress" 的占位数（函数 Y），连同 pendingImageIds 一起传给图片网格 generated-image-gallery；已完成的渲染真图，pending 的渲染 ImageLoadingState（动画占位）。

3.2 起点时间戳：客户端自己记表

当渲染层第一次观察到某会话里存在 src == null 的生图条目时，atom 副作用调用登记函数（反混淆后）：

// app-initial：登记“生成开始时间”，Map<conversationId, Map<imageId, startedAtMs>>
function recordGenerationStart(store, conversationId, imageIds, now /* Date.now() */) {
  store.set(startedAtMapAtom, conversationId, (prev) => {
    const next = new Map(prev);
    let changed = false;
    for (const id of imageIds) {
      const old = next.get(id);
      if (old == null || now < old) {   // ← 保留【最早】时间戳（重挂载/刷新不重置进度）
        next.set(id, now);
        changed = true;
      }
    }
    return changed ? next : prev;   // 引用不变 → 不触发多余渲染
  });
}

网格组件随后按 generationStartedAtMs = startedAtMap.get(pendingImageIds[i]) 逐个传给占位组件。注意：这个时间晚于或等于服务端真实开工时间（取决于用户何时打开界面），因此进度百分比本身连“从请求发出的耗时”都未必准确——它衡量的是“占位组件被观察到之后的耗时”。

3.3 进度曲线：分段线性 + 指数渐近（逐行反混淆）

// image-loading-progress-badge：进度计算（纯函数，输入=已耗时毫秒）
const CONTROL_POINTS = [
  // [归一化时间 t(=elapsed/45000), 进度%]
  [0.00,  3],   // 0 s     →  3%
  [0.10, 25],   // 4.5 s   → 25%
  [0.55, 58],   // 24.75 s → 58%
  [0.85, 88],   // 38.25 s → 88%
  [1.00, 90],   // 45 s    → 90%
];

function computeProgress(elapsedMs) {
  const t = Math.max(0, elapsedMs / 45_000);
  for (let i = 1; i < CONTROL_POINTS.length; i++) {
    const [t0, p0] = CONTROL_POINTS[i - 1];
    const [t1, p1] = CONTROL_POINTS[i];
    if (t <= t1) {
      const k = (t - t0) / (t1 - t0);          // 段内插值比例
      return Math.floor(p0 + k * (p1 - p0));   // 分段线性
    }
  }
  // 超过 45 s：指数渐近逼近 99，永不触顶
  return Math.min(99, Math.floor(90 + 10 * (1 - Math.exp(-1.5 * (t - 1)))));
}

3.4 徽章组件：500ms 轮询 + 可见性门控（反混淆）

function ImageGenerationProgressBadge({ generationStartedAtMs, isActive = true }) {
  const [progress, setProgress] = useState(() => computeProgress(0)); // 初始 3%
  const hostRef = useRef(null);

  useLayoutEffect(() => {
    const tick = () => {
      const p = computeProgress(Date.now() - generationStartedAtMs); // 每次按墙钟重算
      setProgress(p);
      if (p === 99) clearInterval(timer);                            // 99% 后停止轮询
      return p;
    };
    const onVisibility = () => {          // 页面隐藏→停表；可见→立即重算+恢复轮询
      clearInterval(timer);
      if (activeRef.current && !document.hidden && tick() < 99)
        timer = setInterval(tick, 500);
    };

    tick();
    if (!isActive) return;
    document.addEventListener('visibilitychange', onVisibility);
    const unobserve = onIntersect(hostRef.current, (visible) => {   // 滚出视口→停表
      activeRef.current = visible; onVisibility();
    });
    return () => { unobserve?.(); document.removeEventListener(...); clearInterval(timer); };
  }, [generationStartedAtMs, isActive]);

  return (
    <span ref={hostRef} className="... absolute end-3.5 bottom-3.5 ... rounded-full
                                   bg-surface-card/80 tabular-nums backdrop-blur-md">
      <PercentFormat value={progress / 100} style="percent" />
    </span>
  );
}

要点：

  • 无累计漂移：每次都用 Date.now() - start 现算，interval 停多久都不影响正确性——后台标签页回来时进度会“瞬间跳到”当前真实值。
  • 三重门控：窗口不可见（visibilitychange）、占位滚出视口（IntersectionObserver，isAnimating）、以及到 99% 后自动停表，避免空转耗电。
  • 徽章用 tabular-nums 等宽数字，数字跳动不抖布局。

3.5 视觉层：Canvas 点阵“微光场”动画

占位卡（image-loading-state）除徽章外的动效是一个手写 Canvas 动画：满铺圆点阵（默认间距 12 px，半径约为间距 ×0.16×N），两个缓动游走的径向影响场（时长 3.6–6.3 s、ease-in-out cubic/bezier 插值）叠加决定每个点的透明度，形成“两团微光在点阵上游走”的效果。工程细节：

  • requestAnimationFrame 节流到 ~30 fps（帧间隔 < 33.33 ms 直接跳过）；
  • 支持 prefers-reduced-motion（降级为静态点阵 + CSS pulse）；
  • ResizeObserver 重算点阵；离屏时取消 rAF；
  • 可选 previewSrc 层：<img scale-125 blur-3xl opacity-70> 的模糊底图——对话内 pending 阶段没有这个层（服务器不推部分图），它只用于已完成图的 blur-up 渐显场景。

3.6 边界与失败路径

  • 取消/失败：turn 变 cancelled 或条目带 failure 时占位直接消失；用量超限（failure.type == "usageLimitExceeded" && limitId == "image_gen"）有专门的限流墓碑 UI。
  • 多图（grid）：image_gen_multi_stream 表示一次出多张，每张各自一个 pending 条目、各自的起点时间戳和徽章。
  • Create Later（排程生图）：另一套异步任务卡，状态机为 queued → in_progress → succeeded/failed（标题 “Creating your image / GIF”），与本文的即时生成占位是不同组件。

4. 对照组 A：公开 API 其实有“真进度”（但产品没用）

OpenAI 公开的 Responses API / Images API 支持生图流式部分图（官方文档 Image generation → Streaming）：

  • 工具参数 partial_images: 0–3：请求 0~3 张渐进中间图；
  • SSE 事件 response.image_generation_call.partial_image（Images API 为 image_generation.partial_image），载荷是 Base64 中间图 + partial_image_index；
  • 文档明确：“请求的张数可能收不满，如果成品出得更快”。

两个值得注意的推论：

  1. 即便是公开 API，也没有数值百分比字段——进度只能由 partial_image_index / 请求数 推。真正“看起来像进度条”的东西，本质是渐进式图片本身。
  2. ChatGPT 桌面端/网页端的对话通道没有使用这套部分图机制（客户端代码零引用）。所以产品 UI 才只能做时间模拟——不是“没接好”，是通道里压根没有这个信号。

7. 工程启示：如何复用这条曲线

如果你的工具（如 AgentWatcher）需要给不可观测进度的长任务配进度条，这套设计值得照抄：

// 可直接复用的伪进度（TypeScript）
export function simulatedProgress(elapsedMs: number): number {
  const t = Math.max(0, elapsedMs) / 45_000;
  const pts: [number, number][] = [[0,3],[.1,25],[.55,58],[.85,88],[1,90]];
  for (let i = 1; i < pts.length; i++) {
    const [t0,p0] = pts[i-1], [t1,p1] = pts[i];
    if (t <= t1) return Math.floor(p0 + (t-t0)/(t1-t0)*(p1-p0));
  }
  return Math.min(99, Math.floor(90 + 10*(1 - Math.exp(-1.5*(t-1)))));
}
// 用法：start = Date.now()；每 500ms：p = simulatedProgress(Date.now()-start)；
// 真实结果到达 → 卸载进度条（永远不要等它走到 100）。
  1. 起步非零 + 前段陡升：4.5 秒给到 25%，用户立刻有“在动”的感知；
  2. 参考时长处（45 s）只到 90%：给慢任务留缓冲；
  3. 渐近逼近 + 99% 封顶：避免“卡在 100% 却没结果”或“提前 100%”，这两个都比慢更伤信任；
  4. 每帧用 Date.now()-start 现算而非累加：挂起/恢复零漂移；
  5. 不可见即停表，可见即重算：省电且不需要精确计时器。

2. 调查路径

官方文档 → 定名 Composer Predictions，确认交互边界（Tab 只填入不发送） ↓ openai/codex 开源仓库 → 协议与执行机构全部可见（Rust） ↓ 确认 CLI 无此功能（TUI 不发起、忽略通知；app-server 返回 method_not_found） ↓ 本机进程侦察 → 桌面端为 Electron(MSIX)，app-server 走本地 unix/ws，抓包价值低 ↓ 解包 resources/app.asar（660MB）→ 主进程逻辑，代号 Cumberbatch ↓ 关键发现：prompt 不在客户端，由服务端配置接口下发 ↓ GET /wham/predictions/config（用 ~/.codex/auth.json 凭证）→ 拿到提示词本体

3. 完整执行链

触发

  • live：turn 完成、用户在线 → 采样率 1.0（必预测）
  • catch_up：切回旧会话 → 采样率 0.5
  1. 拉配置　GET chatgpt.com/backend-api/wham/predictions/config（认证请求，react-query 缓存 5 分钟）
  2. 资格校验（任一命中即放弃，回报 ineligible）：collaborationMode == plan ／ 线程模型 ∈ unsupported_models ／ modelProvider ≠ openai
  3. 采样　Math.random() ≥ rate → 静默放弃
  4. 生成　thread/sample { threadId, expectedTurnId, prompt, effort, turnTrigger:"composer_predictions", disableMcp, … }，
    注：这是桌面端 runtime 的调用签名；本地 codex-cli 0.167.0 的 ThreadSampleParams 只有 9 个字段，字段名串里没有 effort 与 serviceTier，推理档只能由父线程继承。 app-server 执行机构：
    • 对当前会话做临时分叉（ephemeral、exclude_turns、不落盘、父会话零污染）
    • 继承完整上下文（含压缩历史）+ 工具/权限/MCP 定义，执行全部阻断
    • 30 秒硬超时（SAMPLE_TIMEOUT），prompt ≤ 4000 字节，输出 ≤ 64 KiB
    • effort 取服务端下发的 prediction_reasoning_effort；为空则回退父线程 reasoningEffort（初版记为固定 high，2026-11-09 复核更正，见 §8）
    • serviceTier 透传父线程值，非固定 priority（初版记为 priority，同上方更正）
    • 护栏：源会话必须 idle 且为 persistent root thread；expectedTurnId 必须是最新结束的 turn；分叉必须 ephemeral；结束后复核 history_version 防陈旧
  5. 解析　响应 text → JSON.parse → 取 .suggestion（zod 校验，null 允许）；工具调用/审批请求一律判 null
  6. 安全过滤　statsig 动态配置 codex-app-cumberbatch-mod-policy + 该源轮次 moderation 元数据 → 命中即丢弃
  7. 展示　输入框幽灵文本；Tab → 可编辑草稿；用户可改可弃；绝不自动发送或自动继续任务
  8. 遥测　codex_prediction_submitted { prompt_version, edited, outcome, model, effort, … }（新版改走 /unified_user_signals，字段见 §8）
初版把当次实拉值（effort=high、service_tier=priority、live=1、catch_up=0.5）写成了固定值。复核确认这些均为服务端下发、可变：客户端读 live_sample_rate / catch_up_sample_rate（缺省 1），effort 为空回退父线程档位，serviceTier 透传父线程。采样率与模型名单仍由 /wham/predictions/config 控制。

4. 提示词本体（prompt_version = 5，2026-10-29 实拉）

This is an app-generated request for a suggested next user message. The user did not write this message.

Your suggestion will appear in the user's empty message composer. They can accept it, edit it, or ignore it; it will not be sent automatically.

Predict the single message this user is most likely to type next from the visible conversation. Use the whole conversation to understand their current intent and the latest exchange. Choose the action and specific object that best continue that intent, rather than a generally useful follow-up. Express its core naturally in the user's voice, keeping the requirements needed to retain its meaning. Choose the strongest grounded move even if several continuations are possible; uncertainty about exact wording or incidental details is not a reason to return null. Use null only when the conversation offers no grounded next move at all.

Set suggestion to exactly one natural user message, one line, at most 240 characters, or null. No alternatives or explanation.

客户端发送前拼接的固定 JSON 后缀（src-D0VLwrLy.js 的 s 函数）：

<prompt>\n\nReturn only JSON matching this schema: {"type":"object","properties":{"suggestion":{"type":"string","nullable":true}},…}

5. 关键结论

  1. 生成模型 = 当前线程同款模型（分叉继承），高推理档、priority 服务档——不是小自动补全模型，这是建议质量高的第一原因。
  2. 提示词服务端下发、版本化（v5），配套接受/编辑率遥测——质量靠 A/B 迭代闭环，不是一次写好。
  3. 输出契约严格：JSON {suggestion: string|null}，一条、一行、≤240 字符、禁止解释。
  4. 提示词五项设计（对应五种失败模式）：反幻觉前言（app 生成请求）→ UX 语义（草稿、不自动发送）→ 反泛化（点名具体对象，禁止"继续"类废话）→ 用户口吻 → 空值校准（措辞不确定 ≠ null，无 grounded 下一步才 null）。
  5. 安全与防滥用三层：资格校验（plan 模式/排除模型）、生成侧无副作用（工具禁执行 + 临时分叉）、输出侧 moderation 过滤。
  6. CLI 无 UI，但引擎在：协议与 TUI 占位已铺好，thread/prediction/request 在开源 app-server 仍是 stub；执行机构 thread/sample 已编译进二进制且可调用（2026-11-09 实测），只是没导出到公开 JSON schema，客户端需在 initialize 声明 capabilities.experimentalApi: true。
  7. 本机复现方式：用 ~/.codex/auth.json 的 access_token + ChatGPT-Account-ID 请求头 GET 配置端点，一次成功（token 不落日志）。

7. 可复用产出（对 AgentWatcher）

  • 提示词模板：§4 可直接改造（把 composer 描述换成卡片建议位），五项设计与输出契约原样保留。
  • 生成引擎：Codex 会话可走 thread/sample（官方发动机，上下文继承 + 护栏免自研）；其他 provider 用任意 API 模型 + 上述提示词。2026-11-09 落地：已打通 app-server 里未导出的 thread/sample（initialize 必须带 capabilities.experimentalApi: true），路径为 thread/read → thread/fork → thread/sample → thread/archive；thread/resume 因桌面端独占 thread-writer-locks 不可用，thread/prediction/request 仍是 stub。实测：短会话 5.0 秒 / 3.4 万 token / 99.5% 缓存命中，622KB 会话 12.5 秒，4.3MB 会话 27 秒（历史全量 prefill 不命中缓存）。因此按 1MB 体积门控，超过回落 codex exec（只带尾部 4 轮，固定约 3.4 万 token）。同日第二轮：采样改为复用「建议专用常驻 app-server」（service_tier=priority + mcp_servers={}，与扫描/handoff 的 server 分开，避免 priority 波及普通 turn 计费）；推理档无法按请求指定——ThreadSampleParams 的 9 个字段里没有 serviceTier/effort，且该服务的 serde 不拒绝未知字段（实测塞 zzzProbeField 也照常返回结果），所以「传了不报错」不能当作字段存在的证据，只能以二进制里的字段名串为准。实测 priority 的 sample 阶段均值 7.0s、default 8.4s（各 6 样本，方向一致但差异在噪声内），fork 阶段 0.2–6.7s 波动最大。
  • 迭代机制：prompt 下发 + 版本号 + 采样率 + 接受/编辑遥测，是质量闭环的关键，值得照搬。
  • 边界：Tab 不自动发送是刻意设计（防 AI 自答循环）；自动化发送若做，仅限 AskUserQuestion 选项作答场景。最新版官方口径进一步明确「don't automatically accept or send follow-up messages」，偏离须显式记录。
附注：本机另发现 ~/.codex/ambient-suggestions/ 为另一功能（项目级主动任务建议，gpt-6-luna 小模型生成、JSON 落盘），与输入框预测无关，但同为"服务端下发 prompt + 本地生成"模式。

8.5 引擎侧硬护栏（app-server/src/thread_sample.rs 源码复核）

  • SAMPLE_TIMEOUT = 30s、MAX_PROMPT_BYTES = 4000、MAX_OUTPUT_BYTES = 64 KiB
  • 源会话 agent_status == Running → 拒绝；snapshot.ephemeral 或非 root agent → 拒绝（必须是 persistent root thread）
  • expectedTurnId 必须是 load_latest_model_context / list_turns 查到的最新一个已完成/失败/中断 turn，否则 sample source turn must be the latest finished turn
  • 分叉强制 config.ephemeral = true、插 AutoCompactionDisabled、session_source:"thread_sample"、thread_source:Feature("thread_sample")
  • 采样循环遇 ExecApprovalRequest / ApplyPatchApprovalRequest / RequestPermissions / RequestUserInput / DynamicToolCallRequest / ElicitationRequest 一律报错终止；collect_response 见任何非 assistant 文本或工具调用即 text = null
  • 收尾复核 parent.conversation_history_snapshot().history_version() != revision → sample source changed 拒绝；随后 shutdown、移除分叉线程、清理 capture 注册

8.6 官方帮助中心口径（2026-11-09 查）

  • 支持模型由 2026-10-09 公告的 GPT-6 Astra / GPT-6.1 Sol，扩到 + GPT-6.1 Terra；本地与 SSH 线程；Work 的本地线程也可能出现
  • 「A prediction won't appear after every response」「The composer may choose to skip a prediction」——不保证每轮都有；数秒延迟、长会话更久，用户无需等待可继续输入
  • 「Predictions don't automatically accept or send follow-up messages」——绝不自动接受或发送；Tab 只把文本放进输入框成为可编辑草稿
  • 只用当前 thread 内已有上下文，不主动查 memory、不拉 connected apps；memory 关闭时同样可用
  • beta 期生成预测不计用量、不消耗 credits；发送（含被采纳的预测）按正常计费

8.7 对 AgentWatcher 的影响

初版 §3 写「live：turn 完成、用户在线」；AgentWatcher 现有 suggestion_should_trigger 却只在新进入 waiting 时触发，而 Codex 的 waiting 来自 waitingOnApproval / waitingOnUserInput（等审批），与「回复完成、等用户下一句」不是同一事件。这是语义错位：即使修好解析、cwd、ID 三处实现断点，绝大多数正常结束的 idle 会话仍不会自动生成建议。另需注意官方「Tab 不自动发送」是刻意设计，AgentWatcher 的 ZCode 自动作答属有意偏离，须在设计里明确标注。
